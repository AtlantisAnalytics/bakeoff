Method

Every week we test new open-weight models on ordinary consumer hardware and publish what we measured, the rules that turned it into verdicts, and the raw data. Anyone can re-run a week.

Tiers

A tier is a hardware envelope: a GPU memory size, or a unified-memory machine. Models are only compared with other models in the same tier. Today's tiers are 12 GB, 24 GB and 36 GB unified. Each tier has a current pick per quality track.

Engines

A model runs on the inference engine its format needs: vLLM for safetensors weights, ExLlamaV3 (served by TabbyAPI) for EXL3 quantizations. Models on different engines compete for the same pick. Every result names its engine, and its bundle records the engine's version. Every engine keeps its KV cache unquantized, at 16-bit precision (vLLM at the model's own FP16 or BF16, ExLlamaV3 at FP16), so differences come from the model and its quantization, not cache settings. We run only pinned upstream engine releases.

Rules v1

Each run is assessed separately for every track it has scores in.

  1. Eligibility. A run must complete, pass bundle verification, reach at least 16K tokens of usable context, and decode at least 10 tokens/s (median, short prompt, one request at a time). Anything else is listed under "Tested, doesn't fit" with the reasons.
  2. The pick is re-measured. The current pick is run again the same week, on the same machine, so every comparison is like for like. Without that control run, a candidate can be at most watch.
  3. Comparable. The candidate and the pick must use the same suites at the same versions, and items are paired by id. Otherwise the pair is not comparable (at most watch).
  4. Score and confidence. A track score is the mean of its suites' accuracies. The difference is candidate minus pick, with a 95% confidence interval from 10,000 paired bootstrap resamples. The random generator is seeded from the week, tier, track and both bundle hashes, so anyone gets the same interval.
  5. Verdict. Replace needs the interval's lower bound above 0, decode speed of at least 0.8× the pick's, and usable context at least as large as the pick's (capped at 32K). Watch means the candidate looks better but the interval includes 0, or it is clearly better but fails the speed or context check, or it is not comparable. Everything else is hold.
  6. New picks. With no pick yet, the best eligible run becomes the initial pick. If several runs replace the pick, the highest score wins (ties go to faster decode, then to the lower run id) and the others are shown as outranked.
  7. No pick at 100%. If a track has no pick yet and its best score is 100%, no pick is named that week. A perfect score shows the suite is too easy to rank those models, and a pick chosen on speed alone could never be replaced, because no run can beat 100%. The track gets its first pick in a later week whose best score is below 100%.
  8. Overrides. The owner can override a verdict. The page then shows what the rules computed, what the owner decided and why.

Judge-model comparisons for open-ended answers are shown for information only. They never change a verdict.

Suites

Quality tracks are scored on public test suites plus our own. Each suite is pinned by a content hash, and a week records the hash it used.

  • General: a GSM8K slice (MIT), an IFEval slice (Apache-2.0) and open-ended prompts (CC BY 4.0; judge-scored, information only).
  • Format: replies that must match exactly while following several rules at once, such as sort, reverse, change case, join and convert (CC BY 4.0).
  • Grounding: questions about an incident log, a release register and a policy with an amendment. Some answers need the corrected value or two facts chained together. Others are not in the document even though the same detail is given for something else, and the answer must say so (CC BY 4.0).
  • Long context: eight vaults with look-alike codes hidden in up to about 11,500 tokens of records. The question asks for one vault's code, for a code that a later notice changed, or for a vault that isn't there (CC BY 4.0).
  • Structured output: JSON extraction with nested objects, arrays of records, enums, null for what the text leaves out, and values to normalise (CC BY 4.0). Every value is checked. It is scored two ways. Strict means the whole answer is valid JSON that matches the schema and the values. Extractable means that JSON can be pulled out of surrounding text. Older bundles did not record extractable, and show "not measured".

Third-party slices keep their authors' licenses and are attributed in the repository.

Measurement notes

Quality is measured on every host that runs the model. Floating-point rounding differs between cards, so the same weights can produce different text on different hosts and occasionally a different pass/fail. A verdict therefore compares a candidate with the current pick re-measured on the same host, item by item, and never compares scores across hosts. When a model runs on several hosts in a week, the week reports how often their pass/fail agreed.

Quality prompts go to the engine eight at a time, each at temperature 0 with a fixed seed. Like a different card, batching on the server can change an occasional token. The candidate and the pick it is compared with are always measured the same way.

The memory figure is what the engine reserved, not what the model needs. vLLM claims a fixed share of the card at start-up and fills it with weights and KV cache. For fit, read the KV capacity and the share of it one request of each size needs.

KV fit: the run records the KV cache's capacity in tokens for its serving config, and the share of it one request of each context size needs. That share assumes full-attention KV on every layer, so for sliding-window or hybrid models it is an upper bound. The capacity holds for that serving config only: another memory share or maximum context gives another pool. The KV cache is kept at the model's own precision (FP16 or BF16; vLLM's cache_dtype "auto"), never quantized.

Reproduce a week

The repository and the raw data become public at launch. Everything is in the repository. Each week's input, the raw bundles for every run, and the week's results sit together under results/<week>/.

git clone https://github.com/AtlantisAnalytics/bakeoff
cd bakeoff
uv sync
uv run bakeoff rederive <week>
uv run bakeoff site --check

bakeoff rederive re-publishes the week from its stored input and bundles in a temporary directory, with the earlier weeks' picks, applies the rules above and compares the result byte for byte with the published week.json. It prints identical or the fields that differ. For a corrected week, the bookkeeping of earlier revisions comes from the published file, because their inputs are kept in the git history. bakeoff site --check confirms the pages were generated from those results. The JSON for any week is at /api/v1/weeks/<week>.json and is described by a JSON Schema at /api/v1/schema/week.v1.json.
